## 1. What you're building

A dashboard for a **digital twin of a 1000 kVA distribution transformer** ("Transformer-1", 415 V, rated current 1391 A, MAHE Bengaluru). The backend does all the computing. The frontend:

1. Lets the user pick a built-in dataset **or import their own file** (the organizers will hand us a dataset at the finale — this flow must work).
2. Shows measured vs twin-predicted temperatures, loading, health index, alerts, recommendations, remaining life.
3. Replays a dataset as if it were a live feed.
4. Shows a self-test panel in CPRI's format and lets the user download a PDF report.

**You never compute engineering values in the frontend.** Display what the API returns. If something's missing, it's a backend question.

## 4. API (call only these)

All endpoints sit under `/api`. Errors come back as HTTP 4xx/5xx with `{ "detail": "<readable message>" }` — **show `detail` to the user**, never a stack trace.

| Endpoint | Purpose | Notes |
|---|---|---|
| `GET /api/health` | Backend up? version | Poll on load; show "Backend offline" banner if it fails |
| `GET /api/datasets` | Built-in + imported datasets | `[{id, label, kind: "scenario"\|"real"\|"imported", simulated, mode}]` |
| `POST /api/import/inspect` | Upload file(s), get proposed mapping | multipart; returns proposal (see §6.1) |
| `POST /api/import/load` | Confirm mapping + asset, register dataset | returns `{dataset_id}` |
| `GET /api/runs/{id}` | Full run result | params: `start`, `end`, `max_points` (default 2000; backend downsamples) |
| `GET /api/runs/{id}/state?t=` | State at time `t` | current values, active alerts, HI, sub-scores |
| `GET /api/runs/{id}/snapshot-table` | Per-record table, worst health first | **snapshot mode only**; may be a stub initially |
| `GET /api/runs/{id}/report.pdf` | PDF report | download; may be a stub initially |
| `GET /api/selftest` | CPRI-format self-test table | |
| `POST /api/alerts/send` | Send status message (Telegram) | returns `{delivered: bool, fallback: bool}` |

### 4.1 Shape of `GET /api/runs/{id}` (indicative)

```ts
{
  dataset: { id, label, simulated: boolean, mode: "full" | "meter_only" | "snapshot" | "data_only" },
  asset:   { rated_kva, lv_v, i_rated_a, tags: Record<string, "Confirmed"|"Assumed"|"Estimated"|"To verify"> },
  capabilities: Record<string, boolean>,      // drives what you show — see §5
  series: {                                   // column arrays, same length as `timestamp`
    timestamp: string[],                      // ISO 8601 with +05:30
    IR: number[], IY: number[], IB: number[], I_mean: number[], IN?: (number|null)[],
    VR?: number[], VY?: number[], VB?: number[],
    loading_pct: number[], amb_C: number[],
    OTI_C?: (number|null)[],                  // measured top-oil
    twin_oil_C: number[], twin_hs_C: number[],
    residual_oil_C?: (number|null)[], fidelity_rmse_C?: (number|null)[],
    ageing_rate_expected: number[], ageing_rate_actual?: number[],
    OLI_pct?: (number|null)[],
    health_score: number[],
    dq_flags: string[]                        // ";"-separated codes, "" if clean
  },
  alerts: Alert[], recommendations: Recommendation[],
  health: Health,                             // latest
  rul: { display: string, years_low, years_high, risk, life_consumed_expected_days, life_consumed_actual_days, ageing_rate_recent },
  plausibility: { OTI: "plausible"|"suspect"|"not_checked", ATI: ... },
  events: ThroughFaultEvent[],                // may be empty
  data_health: DataHealthReport,
  gt_markers?: { scenario_id, fault_label, fault_start }   // scenarios only — show as a marker, label "injected fault"
}
```

`null` = missing value (backend sends `null`, never `NaN`). Draw gaps, don't connect across them.

### 4.2 Core objects

```ts
Alert = { id, timestamp, module: "overloading"|"insulation"|"short_circuit"|"electrical"|"oil"|"moisture"|"data",
          type, severity: "info"|"warning"|"critical", origin: "asset"|"sensor",
          detector: "rule"|"residual"|"ml"|"physics", value, threshold, explanation,
          recommendation_id, simulated: boolean, lead_time_h: number|null }

Recommendation = { id, action, test, urgency: "immediate"|"24h"|"7d"|"next_scheduled",
                   rationale, alert_id, standard_ref }

Health = { score: number, band: "green"|"yellow"|"red", capped: boolean,
           components: { thermal, ageing, loading, electrical, integrity, fault_stress },  // missing = not available
           weights: {...} }
```

## 5. Modes and capabilities (most important rule)

The backend tells you what the dataset supports. **Never check for columns yourself — use `mode` and `capabilities`.**

| `mode` | Meaning | UI |
|---|---|---|
| `full` | Has measured oil temperature | Everything available |
| `meter_only` | No oil temperature sensor | Show **estimated** temps (label "Estimated by twin"), hide residual & fidelity, show note "Running on meter data only" |
| `snapshot` | Records with no timestamps | **No time charts, no replay.** Show the ranked records table (§6.9) |
| `data_only` | Twin can't run (e.g. no current) | Show Data Health + raw data; banner explaining what's missing |

Capability flags (confirm exact names in `docs/API.md`) → what to hide when `false`:

| Capability | Hide / change when false |
|---|---|
| `residual_fidelity` | Residual chart, fidelity number, residual alerts filter |
| `unbalance` | R/Y/B unbalance figures |
| `voltage_quality` | Voltage panels |
| `neutral_current` | Show "neutral (proxy)" label instead of measured |
| `oil_leak_theft` | Oil level module → "not available for this dataset" |
| `through_fault` | Short-circuit module → "needs event log" |
| `ageing_rul` | RUL card |
| `breathing` | Moisture exposure item (may be cut entirely) |

Hidden panels show a **short reason**, not blank space: "Not available — dataset has no oil level channel."

## 6. Pages

Left navigation, in this order. Header + SIMULATED banner on every page (§7).

### 6.1 Import  *(must-have — the finale depends on it)*

Flow:
1. **Upload** CSV/XLSX (drag & drop + button). Multiple files allowed.
2. `POST /import/inspect` → show:
   - Sheet picker (if Excel with several sheets; backend proposes a role per sheet: trend / events / nameplate / other).
   - **Mapping table:** source column → dropdown of canonical names, prefilled with the proposal, confidence shown (low confidence highlighted). Unmapped = "Ignore".
   - **Unit dropdown** per mapped column (prefilled suggestion).
   - **Timestamp column** picker + **"Dates are day-first (DD/MM)"** toggle (default ON). If no timestamp found: show the backend's message and options — "Treat as records (snapshot mode)" or "Assign times: interval [15 min] starting [date]".
   - **Asset form:** rated kVA, LV voltage (V), optional losses — prefilled from Transformer-1; computed rated current shown read-only.
   - **Preview:** first 10 rows + small plots of mapped current, loading %, temperatures; backend range warnings shown inline ("Loading 4000% — check units").
3. **Load** → `POST /import/load` → navigate to Data Health for the new dataset.

Target: someone who's never seen the file gets it running in **under 2 minutes**.

## 7. Global UI rules (non-negotiable)

1. **SIMULATED banner** whenever `dataset.simulated` is true, on every page. Every simulated alert gets a small "SIMULATED" tag. This is a hackathon fair-play requirement, not decoration.
2. **Phase names are R / Y / B** (Indian convention). Never L1/L2/L3 or A/B/C in the UI.
3. **Green / yellow / red only for health state** (HI band, module status). Not for line colors or decoration.
4. **Measured = orange, twin = blue**, consistently across every chart.
5. **Units always shown:** °C, A, V, pu, %, kVA. Temperatures 1 decimal, currents whole amps, pu 2 decimals.
6. **Bench vs operating:** 50 A and 60 °C appear **only** on the Self-Test page.
7. **Estimated / assumed values are labeled** (twin-estimated temperatures, estimated rating, proxy neutral current).
8. **Timezone:** display Asia/Kolkata (IST); backend timestamps already carry +05:30.
9. **Never invent values.** Missing → "—" with a tooltip reason.

## 8. Header & replay

**Header:** asset identity (from `asset`), dataset selector (`GET /datasets`), mode indicator (and a Full / Meter-only toggle for scenarios — call the backend with the mode parameter if provided, otherwise hide), replay controls, current replay timestamp.

**Replay — do it client-side:**
- Fetch the run once (`GET /runs/{id}`), keep it in memory.
- A replay cursor (index) advances on a timer: speeds 60× / 240× / 1440× (1 day ≈ 1 min / 15 s / 1 s).
- **[P4]** Speed labels show transformer time ("1 day/min", "1 day/15 s", "1 day/s"). A **"Jump to injected fault"** button (scenarios only, uses `gt_markers.fault_start`) moves the cursor to 1 day before the fault.
- Charts show data **up to the cursor**; cards show values **at the cursor**; alerts appear when `alert.timestamp <= cursor`.
- Play / pause / scrub slider / jump-to-next-alert.
- Use `GET /runs/{id}/state?t=` only if you need server-computed state at an arbitrary time; otherwise derive from the loaded run.
- No WebSockets needed.

## 15. [P4] 3D Twin: Overview layout and behaviour

This section is the frontend's own design (Ahana's sketch + team decisions). It uses only data from the API above and adds no engineering calculations.

### 15.1 Layout (Overview)

```
┌──┬──────────────────────────────────────────────────────────────────────────┐
│≡ │ [▲ ALARM: WATCH] Transformer-1 · 1000 kVA │ dataset ▾ │ FULL │ ◀ ▶ 1 day/s │ header
│  ├──────────────────────────────────────────────────────────────────────────┤
│◉ │ SIMULATED — Scenario S2 (cooling degradation)                            │ banner
│  ├──────────────────────────────────────────────────────────┬───────────────┤
│▤ │                                                          │ ‹  DRAWER     │
│  │  ┌glass box┐                                             │  (glass)      │
│⚠ │  │Radiators│────╮          3D TRANSFORMER                │  Health Index │
│  │  └─────────┘     ●   [X-ray] [Blueprint] [Reset view]    │  Top-oil      │
│⇪ │                                                          │  Loading R/Y/B│
│  ├──────────────────────────────────────────────────────────┤  Life / RUL   │
│… │ Overloading ● │ Insulation ● │ Short circuit ● │ Oil ●    │               │ module strip
│  ├──────────────────────────────────────────────────────────┴───────────────┤
│  │ ━━━━━━━━━━━━━━━●━━━━━━━━━━━━━  21 Apr 14:15 IST   [Jump to fault] [Next ⚠]│ scrub bar
│  └──────────────────────────────────────────────────────────────────────────┘
│    ↓ scroll: main measured-vs-twin chart · latest alerts · recommendations · Download report
```

- **Alarm indicator** (header, far left): shows the worst part status, as the chip words **NORMAL / WATCH / CRITICAL**. It is grey "NO DATA" when the backend is offline. Clicking it opens a dropdown of recent alerts; clicking an alert focuses that part.
- **Right drawer** (360 px, glass): holds the four §6.3 cards stacked. It is **closed by default**, opens with the `‹` arrow, and **opens automatically when the alarm rises** to WATCH or CRITICAL. The canvas shrinks rather than being covered.
- On other pages the header, banner and replay controls stay; the drawer is Overview-only.

### 15.2 Model
- `public/models/transformer_parts.glb`: about 4.6 MB, about 12k triangles, textured. "High voltage power transformer" by **Showdoze** (Sketchfab), **CC-BY-NC 4.0**. Footer credit on every page: "3D model: Showdoze (Sketchfab), CC-BY-NC 4.0".
- It has been split into 28 named meshes by `tools/split_glb.py`. `docs/model_parts_preview.png` shows the part colours.
- Mesh name prefixes: `tank*` (tank + fittings), `conservator`, `radiator*` (banks, headers, pipes), `bushing*` (6 bushings + 6 bases).
- **Built in code:** windings `winding_r` / `winding_y` / `winding_b` (copper coils, R/Y/B) and a laminated `core` inside the tank bounds. They are visible in **X-ray** mode (the tank fades to about 15 %).
- **Fallback:** an `ErrorBoundary` + `Suspense` fallback builds a primitive transformer with the same part ids if the `.glb` fails.
- In the pitch: "representative 3D model". The data is Transformer-1's.

### 15.3 Parts: readings and alert placement

| Part | Readings shown (from `series` at the cursor) | Alerts placed here (by `module` / `type`) |
|---|---|---|
| **Windings** (R/Y/B) | `IR, IY, IB, I_mean, loading_pct`, `twin_hs_C`, `ageing_rate_actual` | module `overloading`, `insulation`, `short_circuit`; electrical current types (unbalance, neutral) |
| **Tank** | `OTI_C` (measured, orange) vs `twin_oil_C` (twin, blue), `amb_C` | top-oil types; `data` alerts on OTI (origin sensor) |
| **Radiators** | `residual_oil_C`, `fidelity_rmse_C` | residual / cooling-degradation types |
| **Conservator** | `OLI_pct` | module `oil` (leak, theft, low level), `moisture` |
| **Bushings** | `VR, VY, VB` | electrical voltage types (high/low, voltage unbalance) |
| **Core** | none | **Not monitored.** Always grey. Tooltip: "Core: not monitored (no sensor)". |

- **Placement is presentation only.** The frontend keeps a lookup table `ALERT_TO_PART` (`twin/parts.ts`) keyed by `type`, with a fallback on `module`. It never changes severity or creates alerts. Unknown types go to "General" in the alert list, never dropped.
- **Request to P3:** add an optional `part` field to `Alert`. When present, the frontend uses it instead of the table.

### 15.4 Part status (derived from API alerts + capabilities)

| Status | Rule | Look |
|---|---|---|
| **CRITICAL** (red) | an asset-origin `critical` alert on the part is active | strong red tint + outline, 1 Hz pulse |
| **WATCH** (yellow) | an asset-origin `warning` alert is active | yellow tint + outline |
| **NORMAL** (green) | no active asset-origin alert | subtle green outline, textures visible |
| **Sensor** (ⓘ badge) | a sensor-origin alert is active | blue-grey ⓘ badge on the part + "Data fault — check the device, not the transformer." Never red. |
| **NO DATA** (grey) | the part's capability is false, or the mode hides it | grey + reason, e.g. "Not available — dataset has no oil level channel" |
| **Estimated** | `meter_only` mode | tank shows "Estimated by twin"; radiators grey (residual hidden) |

- **"Active" alert:** visible once `timestamp <= cursor`. It stays active for **24 h of replay time** after its timestamp unless a later alert of the same type and part supersedes it. **[Open — confirm with P3]** whether alerts have a clear/end time; if they do, use it instead.
- **Anti-flicker:** colour upgrades show immediately; downgrades show after 3 cursor steps.
- **Snapshot mode:** no replay. The 3D view colours parts for the **selected record** (row click in §6.9).
- **data_only mode:** all parts grey, with the banner from §5.

### 15.5 Interaction

| Trigger | Result |
|---|---|

### 15.7 Blueprint mode (nice-to-have, first to cut)
While **Blueprint** is on, hovering a part works like this:
1. The rest of the model fades to about 10 %.
2. The part is drawn as **edge lines** (drei `<Edges>`, `--blueprint`) on a faint grid.
3. **Solid** callouts show:
   - part name and function (static text in `parts.ts`)
   - **specs from `asset` with their tags** (Confirmed / Assumed / Estimated / To verify)
   - which channels watch it (from `capabilities`)
   - the status chip

**No invented dimensions or values:** a missing spec shows "— (nameplate pending)". The corner label reads "Representative model · specs per asset". Click still opens the detail box.

| Part | Function text |
|---|---|
| Windings | Carry load current (R/Y/B); hot-spot temperature drives insulation ageing |
| Tank | Holds core, windings and insulating oil |
| Radiators | Dissipate oil heat to air (ONAN cooling) |
| Conservator | Oil expansion reservoir; breathes through a silica-gel breather |
| Bushings | Insulated HV/LV terminals |
| Core | Magnetic circuit (laminated steel), not monitored |
